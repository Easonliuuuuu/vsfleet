# Repository and release security

This page records the controls that protect what runs with vsfleet's
release authority: pinned workflow dependencies, repository rules, the
publishing credentials, and what to do when one of them is compromised.
[Vulnerability scanning](security-scanning.md) covers known vulnerabilities
in the code and image.

vsfleet has one maintainer, who is the only collaborator and holds the
admin role. No control here provides independent review; see
[solo-maintainer limits](#solo-maintainer-limits).

## Workflow dependencies

Every action in `.github/workflows/` is pinned to a full commit SHA, with
the release it came from in a comment:

```yaml
- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

A version tag can be moved to different code after review; a commit cannot.
`scripts/check-action-pins.sh` rejects any other form of reference,
including reusable workflows, and runs as the `Pinned actions` job on every
pull request. The repository's Actions setting "Require actions to be pinned
to a full-length commit SHA" enforces the same rule when a workflow starts.

Dependabot proposes new pins weekly, moving the SHA and the comment
together, and skips action releases younger than seven days. To review an
update, read the upstream diff between the two commits, not just the release
notes. To pin a new action by hand:

```sh
gh api repos/OWNER/REPO/commits/vX.Y.Z --jq .sha
```

Then check that the commit is on the upstream repository's default branch
or a release tag, not only in a fork.

Two composite actions call other actions; both pin them by SHA upstream:
`actions/upload-pages-artifact` uses `actions/upload-artifact`, and
`dominikh/staticcheck-action` uses `actions/setup-go` and `actions/cache`.
Changing either pin changes those nested commits too, so review them in the
same diff.

### Tools the workflows download

Dependabot does not see version inputs or install scripts. Bump these by
hand:

| Tool | Pinned in | How it is verified |
| --- | --- | --- |
| GoReleaser | `version:` of `goreleaser-action` in `ci.yml` and `release.yml` | exact release; downloaded by the pinned action |
| Staticcheck | `version:` of `staticcheck-action` in `ci.yml` | `go install` checked against the Go checksum database |
| kind and kubectl | `kubernetes.yml` | exact releases; downloaded by the pinned action |
| Cosign | v2.5.2, the default of the pinned `sigstore/cosign-installer` | the installer checks a SHA-256 kept in the action, then the release signature |
| govulncheck, grype | `scripts/install-scanners.sh` | Go checksum database; SHA-256 of the grype archive |

The rest are deliberately not pinned to one build:

- **Go:** `setup-go` installs the newest Go 1.26 patch release so security
  fixes arrive without a pin change;
  [vulnerability scanning](security-scanning.md#triage) explains why.
- **Documentation:** `requirements-docs.txt` pins the top-level packages
  but not their dependencies or hashes. The docs job has no publishing
  secrets; GitHub Pages deploys from a separate job.
- **Runner images:** `ubuntu-latest`, `macos-latest`, and `windows-latest`
  move with GitHub's image releases.

### Workflow dependency lockfiles

GitHub's [workflow dependency lockfiles](https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles)
(`.github/workflows/actions.lock`, generated by `gh actions-lock`) also lock
nested actions and check the source repository's identity when a workflow
runs. vsfleet uses SHA pins instead, for now: the lockfile documentation
does not say whether the feature is available to user-owned repositories,
and Dependabot updates SHA pins today. Revisit this once Dependabot supports
lockfiles; the lockfile satisfies the same pinning setting.

## Repository rules

| Ref | Rule | Effect |
| --- | --- | --- |
| `main` | Pull request required, squash merge only | No direct pushes; every change is one reviewed commit |
| `main` | Required checks: `Go vulnerabilities`, `Pinned actions` | A pull request cannot merge while either fails |
| `main` | No deletion, no force push | History cannot be rewritten |
| `refs/tags/v*` | No update, no deletion, no force push | A published release tag cannot be moved to different code |

Both required checks come from `vulnerabilities.yml`, which runs on every
pull request, so documentation-only pull requests are not left waiting for
a check that never reports.

The admin role may bypass the `main` rules when merging a pull request. Keep
that for emergencies, such as a broken required check, and say so in the
pull request. Direct pushes are blocked even for the admin.

Actions settings:

- The default `GITHUB_TOKEN` is read-only; each job asks for the permissions
  it needs.
- "Allow GitHub Actions to create and approve pull requests" stays on,
  because release-please opens the release pull request. With no required
  approvals, Actions approval does not bypass anything.
- The `github-pages` environment deploys only from allowed branches.

## Publishing credentials

| Secret | Used by | Grants | Scope it to |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | release-please, GoReleaser, GHCR, keyless image signing | per job `permissions:` | the `release.yml` jobs only |
| `TAP_GITHUB_TOKEN` | GoReleaser Homebrew formula and cask | push to `Easonliuuuuu/homebrew-tap` | a fine-grained token with Contents read and write on `homebrew-tap` only |
| `WINGET_GITHUB_TOKEN` | GoReleaser WinGet manifests, the WinGet pull request check | push to the `winget-pkgs` fork and open a pull request on `microsoft/winget-pkgs` | a classic token with `public_repo`; cross-repository pull requests need it |

Give each personal access token an expiry of at most one year, and put the
renewal date in your calendar. To rotate one, create the replacement, update
the Actions secret, and revoke the old token. CI's release snapshot uses
placeholder tokens, so the next real release is the first use of a new one;
the `Release` workflow checks that the WinGet pull request was opened. Review the account's
tokens and authorized OAuth and GitHub Apps when rotating.

Image signatures are keyless: Cosign signs with the `release.yml`
workflow's OIDC identity, so there is no signing key to store or rotate.

## Maintainer account

Releases are only as trustworthy as the maintainer's GitHub account. Use a
passkey or hardware security key as the second factor, keep recovery codes
offline, and recheck both when rotating tokens. Do not record credential
identifiers or recovery details in the repository or its issues.

## If something is compromised

Act in this order when a token, the maintainer account, an action, or a
release looks compromised:

1. **Stop publishing.** Disable Actions for the repository, or the
   `Release` workflow, so nothing further is published.
2. **Revoke credentials.** Revoke `TAP_GITHUB_TOKEN` and
   `WINGET_GITHUB_TOKEN`, sign out other sessions, and review the account's
   tokens, SSH keys, and authorized apps.
3. **Find what changed.** Read the account and repository audit logs, the
   `Release` workflow runs, recent pushes to `main` and tags, and the
   `homebrew-tap` and `winget-pkgs` histories.
4. **Check released artifacts.** Compare the archives against
   `checksums.txt` and verify image signatures against the expected workflow
   identity. Mark any affected release as such, delete tampered assets and
   image tags, and revert tampered formula or manifest commits.
5. **Publish and recover.** Open a security advisory naming the affected
   versions, rotate every credential, re-enable Actions, and ship a clean
   patch release.

If an upstream action is compromised, pin the last known-good commit, or
remove the action, before re-enabling workflows.

## Solo-maintainer limits

These controls are not available, or mean nothing, with one maintainer:

- **Independent review.** Required approvals would be self-approvals;
  `main` requires none. Required checks, pinned dependencies, and squash
  merges are the compensating controls.
- **Code owners.** A `CODEOWNERS` file naming the only maintainer adds no
  review.
- **Release approvers.** A deployment environment with required reviewers
  would also be self-approved, so `release.yml` does not use one.
